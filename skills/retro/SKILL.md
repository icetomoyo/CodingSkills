# Retro(会话复盘)

用户要求做一次**复盘**。目标不是评价这次会话好不好,而是找出**环境**里可改的地方,让以后的运行更省事:仓库布局、自动检查、编码规范、steering 文件、工具、信息通道。范围是环境,而非这次会话写下的代码。

## 步骤

1. **读写作风格指南。** 调用 `writing-for-agents` skill,取它的写作风格与审计方法论——候选建议的措辞按它写。完成判据:已调用并拿到该 skill 的内容。

2. **读 primary sources。** 读用户指定的那次会话的原始记录(本机 session 日志:turn、工具调用、文件读写、失败与重试),不用记忆里的摘要代替。用户没指定就默认当前会话。完成判据:已读到原始记录,并能点出其中的具体 turn / 命令 / 文件。

3. **按七类找候选。** 逐类过一遍;触发条件不成立的显式记"跳过"并写一句理由。完成判据:七类每一类都落到"有候选"或"跳过 + 理由"。

- **导航**:agent 找到正确文件有多难?文件之间有没有**隐藏依赖**?补一条**导航指针**会不会更快?**用在**会话里为找某条信息花了很长时间时。
- **自动检查**:有没有能抓住 agent 所犯错误的自动检查?lint、类型、测试、filesystem linter?先读仓库自己的检查命令(`package.json` / 构建工具的 `lint` / `check` 脚本、CI workflow)——一个**已经存在**却未接线、或静默坏掉的检查,就是 finding,不是重造一个。仓库没有任何**护栏**(既无 pre-commit hook,也无 CI job 跑它的 lint / typecheck / test 命令)本身就是 finding:未受 lint 的仓库是常年错过的机会,不是中性默认。**用在**agent 犯了自动检查本可抓住的错,或仓库压根没有护栏时。
- **编码规范**:该给**评审 agent** 一条新规则去执行吗?现有规则该删、该说清吗?先给违规分类:**机械性违规**(固定语法模式、被禁 API、import 形状、文件位置规则)一律换成**确定性检查**——仓库自己 linter 的自定义规则、新 pre-commit hook、或新 CI job,哪个在仓库的语言与现有护栏下最便宜就用哪个。默认**造检查**而不是写规则。`CODING_STANDARDS.md` 只留真正的**判断题**(跨文件一致性、"和周围风格一致"、任何护栏永远替代不了的东西)。**用在**评审 agent 没抓住某个错误时。
- **全局 AGENTS.md**:有没有 steering 指令该移到编码规范(或自动检查)去?**用在**AGENTS.md 特别大时——仓库里的,或用户全局作用域的。
- **工具经济**:agent 有没有做本可精简的昂贵工具调用?有没有特别 token 不友好的自建工具(CLI、MCP)?**用在**agent 做过昂贵工具调用时。
- **空操作**:steering 文件里有没有**不改变 agent 行为**的指令?no-op 的判定用 `writing-for-agents` 里的那条测试(*相对默认行为改变了什么?*)。**用在**steering 文件又大又难使时。
- **信息获取**:有没有办法扩大 agent 的信息通道?tee 开发服务器日志、给第三方服务的只读访问。**用在**某条关键信息对 agent 不可用时。

4. **排序并呈现。** 按**严重度**排:先看下次会话重犯的代价,再看覆盖广度,最后看落地成本(便宜的优先)。每条候选写齐三项——**类别**、**证据**(会话里的具体 turn / 命令 / `文件:行`)、**建议动作**(写进哪个文件、改什么、由实现 agent 还是评审 agent 施加)。完成判据:清单有序,且每条都写齐类别 / 证据 / 建议动作。

## 参考

### 实现 vs 评审

所有工作都过两个阶段:实现与评审。实现 agent 的**上下文压力**最大——探索、写码、调失败都归它。评审 agent 的上下文压力最小——它拿到一份 diff,不用探索,常常也不用写码和调试。

所以**编码规范该由评审 agent 施加,而不是实现 agent**:把规则加给实现 agent,等于从最紧的那块上下文里抢注意力。

### 文件

- `CLAUDE.md` / `AGENTS.md`:会被推进任何在本仓库工作的 agent 的上下文窗口。极其克制地用,通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`:评审时读,实现时不读。文件超过 1,000 行时,往里加指向 docs 目录的导航指针。
- Docs:当参考文件用,由其他文件指向它。写新 doc 之前先找已有的。
- Skills:用来装 doc(它的 `description` 会进 agent 上下文窗口),或装用户调用命令。写法遵循 `writing-for-agents`。

## 本仓库产物

复盘时优先查这些落点有没有跟上这次会话——它们是本 skill 体系的事实源:

- `docs/FEATURE_LIST.md`:这次做完的 feature 是否已转 Completed、Released 版本是否已填。
- `docs/KNOWN_ISSUES.md`:会话里踩到的坑是否已登记;没登记的坑下次会话还要再栽一次,那是**信息获取**或**导航**候选。
- `docs/features/v{VERSION}.md` 设计块:Part A / Part B 是否还描述真实接口,还是已和实现漂移。
- `.agent/handoff/HANDOFF.md`:上次交接的"下一步 / 避坑墓碑"这次是否真被用上;完全没读到它,是**导航**候选。
- `AGENTS.md` / `CLAUDE.md`:是否在膨胀;有没有该下沉到 `CODING_STANDARDS.md`、docs 或 skill 的内容。

## 完成判据

- [ ] 读过该会话的 primary sources(session 日志本身,不是印象)
- [ ] 七类都检查过,或已显式记为跳过并写了理由
- [ ] 候选按严重度排好序
- [ ] 每条候选都写明了类别 / 证据 / 建议动作

## 与其他 skill 的关系

- `writing-for-agents`:第 1 步调用,取写作风格与审计方法论;候选建议的措辞按它写。
- `issue-manager`:候选里属于缺陷的(该修而非该改环境的),交给它登记进 `KNOWN_ISSUES.md`。
